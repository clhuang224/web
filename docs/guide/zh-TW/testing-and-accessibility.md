# 測試與可及性

一個功能可以有正確的算法，卻沒有成功載入圖片；也可以看起來正常，卻無法用鍵盤操作。讀測試時，要先知道它建立了哪一種證據。

## 現有檢查各自負責什麼？

| 檢查                    | 可以發現的問題                             | 沒有直接證明的事                       |
| ----------------------- | ------------------------------------------ | -------------------------------------- |
| TypeScript / vue-tsc    | 型別、欄位和呼叫是否符合宣告。             | runtime 訊息一定正確、畫面一定可操作。 |
| ESLint                  | 專案指定的程式規則。                       | 所有邏輯都符合產品需求。               |
| Vitest 純規則與內容測試 | 路由、換組、回應解析、資料清單的一些條件。 | 真實 Lynx 畫面、網路與裝置行為。       |
| Build 與輸出檢查        | 編譯能完成、必要產物存在。                 | 正式主機能載入所有資產。               |
| 瀏覽器與裝置檢查        | 特定環境下可見的行為。                     | 所有版本、輸入方式與輔助工具都正常。   |

測試來源集中在[原始碼地圖](source-map.md)。不要把某一欄通過解讀成整張表都通過。

## 輪播測試為什麼不直接測每個函式內部？

現有測試追一整輪，確認每張圖是否剛好出現、是否回到開頭，以及往前切換和版面對齊是否合理。它觀察規則帶來的結果，比照著每行實作寫一個相同計算更能指出需求是否被破壞。

但計時器和 `@tap` 不在純算法裡；要驗證暫停、恢復、離開頁面後清除 interval，仍需另外檢查元件生命週期與互動。

## 為什麼 accessibility-role 還不夠？

這個專案使用 Lynx 元素，Web 上並非每個控制項都直接成為原生 `<button>` 或 `<a>`。元件宣告的語意，需要在實際 runtime 中抵達瀏覽器可及性樹，並配上輸入行為。

[accessibility.ts](https://github.com/clhuang224/web/blob/main/src/host/accessibility.ts) 讀取 Lynx 宣告的 role、label 等屬性，補上瀏覽器 role、ARIA、tabIndex、焦點樣式，並將 Enter 或按鈕的 Space 操作轉成啟動行為。

這是本專案對 Web Core 的轉接，會接觸 runtime 的 shadow root 結構。它需要隨 runtime 更新重驗，不應被描述成已經自動解決所有可及性問題。

## 實際要看哪些操作？

先用鍵盤走過側欄、語言選擇、輪播控制、作品連結和返回。確認焦點看得到、順序合理、Enter 和 Space 的用途符合控制項語意，並注意頁面切換後焦點去了哪裡。

再用輔助工具檢查名稱、角色、目前頁面和按下狀態。App 內網頁視窗還要看開啟與關閉時的焦點管理；有關閉按鈕並不能單獨證明整個視窗互動完整。

減少動態效果也要分環境看。Web host 會監看媒體查詢；目前 standalone 狀態以 `reducedMotion: false` 起始，未看到同等的原生偏好同步。因此應把原生偏好列入待驗證與待補接點。

## 什麼時候跑哪些檢查？

主站已有 `pnpm run lint`、`typecheck`、`test`、`format:check`、`check` 和 `build`。讀取 [package.json](https://github.com/clhuang224/web/blob/main/package.json) 可以核對組合方式；主站 CI 目前執行 `check` 與 `build`。

只改文件時，重點是格式、連結、程式摘錄和說明是否吻合。改純規則時，先跑相關測試。改畫面、bridge 或 runtime 時，再補對應的瀏覽器與裝置檢查。

每份驗證紀錄應寫環境、操作與結果。這樣後來的讀者才能分辨「有這個實作」與「這個情境已被確認」。
