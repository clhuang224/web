# 延伸實驗與驗證

前面的章節說明網站已經採用的做法。這一章則整理尚未完成的實驗設計，用同一個專案繼續研究規則重用、資料更新和平台行為。

每個實驗都先列出問題與目前起點，再安排驗證方式。完成實作和檢查之後，才加入結果；下列步驟本身不代表功能已經存在。

## 實驗一：在文件裡操作輪播規則

### 想回答的問題

輪播的換組函式沒有依賴 Vue 或 Lynx，是否能直接用在 VitePress 的互動解說中？如果能重用，還有哪些行為必須回到真正的 Lynx 元件驗證？

### 目前起點

[輪播章節](carousel.md)的 `visibleCount`、`alignIndex` 和 `stepIndex` 只處理輸入與索引。計時器、播放狀態和事件則留在 VueLynx 元件中。

### 驗證方式

1. 在文件專用的瀏覽器 Vue 元件中匯入這三個純函式，加入每組張數、目前索引、上一組和下一組控制。
2. 使用目前的 14 張資料，確認完整一輪、反向切換和手機轉桌面的對齊結果。
3. 改用 15 筆測試資料，觀察最後一組不足兩張時的計算結果。
4. 對照真正的輪播，分別記錄規則結果，以及 `tap`、計時器、圖片載入等元件行為。

這個實驗若完成，可以證明規則能被另一個畫面使用。文件中的瀏覽器按鈕仍不會替 Lynx 事件、手勢或 Android 效果建立驗證。

## 實驗二：GitHub 資料改成建置時快照

### 想回答的問題

作品頁目前在執行時請求 GitHub。若改成建置時產生快照，資料可用性、更新頻率與頁面維護會有什麼差異？

### 目前起點

[GitHub 資料章節](github-data.md)使用公開 API 和共用解析函式。請求失敗時，作品仍然存在，但附加資訊會省略。

### 驗證方式

1. 在實驗分支加入快照產生步驟，沿用現有解析函式，只保留頁面需要的欄位，另外記錄快照產生時間。
2. 比較目前即時請求與快照版本，分別觀察正常網路、API 失敗和無法更新快照的情況。
3. 確認頁面能說明資料的更新時間，並區分沒有星星與沒有取得資料。
4. 記錄 API 請求次數、資料新鮮度、建置失敗時的處理，以及需要額外維護的檔案。

目前專案尚未採用快照。這個實驗的結論應根據相同條件下的紀錄，決定是否值得改變現有資料流。

## 實驗三：原生動態偏好與生命週期

### 想回答的問題

Web 端會接收減少動態效果的偏好，原生端目前沒有同等的同步。Android 的系統設定、背景切換和視窗尺寸改變，應該如何影響輪播？

### 目前起點

[原生章節](native-exploration.md)列出 Web 與 Android 現有的差異。Web host 監看媒體查詢；standalone 狀態以 `reducedMotion: false` 起始，寬度與安全區也在啟動時取得。

### 驗證方式

1. 先在相同裝置與專案版本上記錄現況：切換動態偏好、進入背景、回到前景，以及改變視窗尺寸。
2. 研究所選 Android host 與 Lynx binding 能提供哪些設定和生命週期訊號，確認資料單位與更新時機。
3. 再設計平台轉接，明確處理系統偏好與使用者手動暫停的關係，避免回到前景就覆蓋原本的選擇。
4. 對照 Web 和 Android 的播放狀態、可見索引、計時器與版面，補上能在各自環境重做的步驟。

這裡尚未指定原生 API 或加入同步功能。先確認 host 實際提供的能力，再決定介面與實作。

## 實驗紀錄要包含什麼？

至少記錄研究問題、專案 commit、裝置與 runtime 版本、操作步驟、觀察結果和仍無法解釋的差異。若有比較兩種做法，也要記錄相同的測量條件。

完成後，再判斷結果應留在實驗紀錄，還是能回到主章節成為已確認的實作說明。

可以回到[閱讀地圖](reading-map.md)，或對照[測試與可及性](testing-and-accessibility.md)選擇適合的檢查方法。
