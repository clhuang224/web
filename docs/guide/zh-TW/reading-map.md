## 整個專案先分成幾層

把一次操作想成這樣：

```text
頁面和元件：訪客做了什麼、畫面要顯示什麼
    ↓ 使用共用狀態與操作
平台轉接：這次操作需要哪一種平台能力
    ↓ 交由瀏覽器 host，或在 standalone 模式處理
規則和內容：頁面身分、有效 ID、翻譯、換組算法
```

這是閱讀方向，不是所有函式都必須經過的固定呼叫鏈。例如輪播直接使用純函式，不需要每換一張都請瀏覽器 host 計算。

| 目錄                    | 主要責任                                     | 讀它時要問的問題                       |
| ----------------------- | -------------------------------------------- | -------------------------------------- |
| `src/pages/`            | 組合一個頁面的內容                           | 這一頁用哪些資料與操作？               |
| `src/components/`       | 重複使用的畫面與互動                         | 元件收到什麼、維護什麼狀態？           |
| `src/content/`          | 文案與作品、文章、塗鴉清單                   | 哪些是編輯內容，哪些是目的地？         |
| `src/domain/`           | 型別、純規則和資料驗證；其中也有共用網路讀取 | 這段程式需要 renderer 嗎？需要網路嗎？ |
| `src/platform/`         | 把應用程式操作接到平台                       | 哪一端擁有這項能力？                   |
| `src/host/`             | 瀏覽器外殼與能力                             | 哪裡需要 `window`、網址或 DOM？        |
| 根目錄設定與 `scripts/` | 建置、開發、預覽與檢查                       | 哪些輸出要一起提供？                   |

實際檔案連結集中在[原始碼地圖](source-map.md)。

## 每篇可以怎麼讀

先看功能與結果，再打開列出的 1～3 個關鍵檔案。把一個輸入一路追到輸出就好；不必為了理解輪播，先熟悉整套打包工具。

讀完後，試著回答：「這個決定如果改掉，會影響哪一層？」這比記住所有檔名更有用。
